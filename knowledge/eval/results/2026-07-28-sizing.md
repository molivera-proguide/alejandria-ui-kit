### Correction (screenshot judging got this wrong)

The initial pass credited G1's "no more empty kanban space" to the agent sizing the grid column to
the card's content, per `anti-examples.md` §7's prescribed fix. **The code shows the opposite:**
`App.tsx:290` passes `style={{ maxWidth: "100%", width: "100%" }}` directly to `TaskCard`. Since
`TaskCard.tsx` applies that `style` prop as an inline style on the root `<article>`, it overrides
`.ds-task--kanban`'s own `max-width: 140px` (inline style beats a class selector regardless of
specificity). The grid column (`repeat(3, minmax(0, 1fr))`) is still wide and unconstrained — the
agent didn't fix the column, it defeated the card's own calibrated cap so the card would stretch to
fill it. Visually this reads as "fixed" (no visible empty space) but it's a **worse** fidelity
violation than the baseline's: before, the component at least held its calibrated ÷2 size; now a
local `style` prop silently erases it. Scored as a 1 (not 3) on dimension 5 — this is exactly the
kind of local override Principle 01 and anti-examples §2/§7 warn against, just applied to sizing
instead of color/variant.

This is a **new gap in the knowledge base**, not covered by the current §7 pair (which assumes the
component has no cap to begin with). Added as a follow-up — see Findings below.

## Findings → fixes (input to loop step 4)

- **G4 — ficha `MetricCard` no longer stretches — confirmed in code, not just screenshot.** The
  four ficha tiles render as compact, content-sized boxes; the generated code passes no
  `style`/`className` to any `MetricCard`, wraps them in a plain `flex-wrap` row, and relies
  entirely on `.ds-metric--ficha { width: fit-content }` (added this session). No further fix
  needed here.
- **G4 — `LineChartCard` no longer fills the viewport — confirmed in code.** No `style` override
  on `LineChartCard` either; `.ds-chart-card { max-width: 280px }` applies unopposed. No further
  fix needed here.
- **G4 — also avoided the §8 hardcoded-heading trap this run.** Used `Card`'s `eyebrow`/`title`/
  `description` slots instead of hand-rolling an `<h1>` with literal `fontWeight`/`letterSpacing`
  (the mistake G1 keeps making, see below) — matches §8's "Right" example exactly.
- **G1 — kanban `TaskCard` stretched via a local `style` override, not fixed.** `App.tsx:290`:
  `style={{ maxWidth: "100%", width: "100%" }}` on `TaskCard`, which overrides `.ds-task--kanban`'s
  own `max-width: 140px` (inline style beats any class rule). The grid column
  (`repeat(3, minmax(0, 1fr))`) stayed wide and unconstrained — the agent didn't size the column to
  the card as §7 prescribes, it defeated the card's own cap instead. → **New anti-example needed**:
  a pair distinct from §7 (which covers a component with *no* cap) — this is a component *with* a
  cap being overridden via a local `style`/`className` prop to force full-bleed. Candidate rule:
  "don't override a shipped component's calibrated `max-width` via a local style prop just because
  the surrounding layout is wide — fix the layout's column/track sizing instead." Feeds
  `component-roadmap.md` and a new `anti-examples.md` entry (§9).
- **G5 — `Asistente` 774px freeze confirmed still present**, at roughly the expected fixed width
  regardless of the (much wider) browser viewport. Matches the already-tracked, deliberately
  deferred item in `component-roadmap.md`. Not a new finding; no action taken.
